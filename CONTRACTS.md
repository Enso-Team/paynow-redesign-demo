# PayNow redesign build: contracts

This file is the technical contract between the three parts of the demo (web, iOS and services), so each can be built and tested on its own.

Scope: Log in, Scan & Pay, and PayNow transfer by mobile number or UEN work end to end. Every other tile opens a placeholder screen.

## Layout

```
./
  latency/    measured.json, network times measured in a real banking app, shared by the services and the public demo
  services/   Java 17, Spring Boot 3, Gradle multi-project, docker-compose (MariaDB 11, Kafka in KRaft mode)
  web/app/    pnpm workspace
    packages/sgqr/          SGQR parser (TypeScript), shared by both front ends
    packages/paynow-form/   the React PayNow form micro-frontend, built to one static bundle
    apps/web/               the web demo shell (entry, mocked Face ID, tabs) that hosts the form
  ios/        SwiftUI app generated by XcodeGen, hosts the form bundle in a WKWebView
```

## Journeys

- **Every tap goes through the intent router.**
- **Face ID runs once per journey, when the user taps:**
  - Log in, before Home.
  - Scan & Pay, before the scanner.
  - PayNow, before the PayNow menu.
- **Pay never asks again**, because the journey's session covers it.
- **Peek Balance, Digital Token, switching tabs and product pages never ask.**
- **Scan & Pay:** Face ID → session → scanner → decode → lookup → form → Pay → poll → sent.
- **PayNow transfer:**
  1. Face ID, then session.
  2. The PayNow menu offers Mobile number, UEN or Scan a QR.
  3. The form opens with an empty proxy field.
  4. The lookup fires 300 ms after the input is a valid proxy:
     - a mobile number is 8 digits starting with 8 or 9
     - a UEN is 9 or 10 characters
  5. The form shows the masked name, then Pay → poll → sent.
- **Peek Balance:** the user presses and holds "Tap and hold to PEEK BALANCE" on the entry page.
  - Each chevron sits 22 px from the text and loops every 2.4 s, linear. It fades in at its outer spot, slides 14 px inward (-7 to +7 px), and fades out. Opacity rises over the first 30% and falls over the last 35%. Reduced motion keeps both chevrons still at full opacity.
  1. The entry page blurs and darkens in place. The blur and veil fade in over 0.3 s, ease-in-out. The hint stays sharp on top.
  2. A white card with 40 px side margins, centred, slides up to sit just above the hint.
  3. The card shows two grey placeholder bars for 0.5 s, then stays empty for 0.8 s or until the data arrives. There's no spinner.
  4. The balance fades in on a compact card. The card then grows upward to show the "as of" time and "Latest transactions (within last 30 days)" with 3 rows of type, date and amount.
  5. Releasing the hold removes the card, and the blur and veil fade out over 0.3 s, ease-in-out.
  6. The client keeps the result for 60 s, so a repeat hold shows the balance on its first frame with no skeleton.
  7. Peek uses the read-only pass (see the auth service). It never shows Face ID, a splash or a login screen.
- **Intents:** `login`, `scanAndPay`, `payNow`, `payQR(payload)`, `overseas`, `apply`. The router holds one pending intent in memory. When Face ID is cancelled, the intent is dropped and the user stays on the entry screen.

## Face ID

- **iOS:**
  - `LAContext` with `.deviceOwnerAuthentication`, so the passcode is the fallback. The prompt names the journey ("Log in", "Scan & Pay", "PayNow").
  - When the device has no biometrics enrolled (the usual simulator case), the app shows a mocked Face ID sheet (glyph, 1.2 s, success) instead.
  - The device key is a P-256 key in the Keychain with `.biometryCurrentSet`. It opens full sessions.
  - The Peek key is a second P-256 key with no biometry, accessible after first unlock on this device only. It opens Peek passes and nothing else, so Peek never shows Face ID.
  - On the simulator, software keys replace the Secure Enclave.
- **Web:** Face ID is always the mocked sheet. The web version exists only so people can see the example.

## First run (device binding)

- When no device key exists, iOS shows "Set up this iPhone".
- The user, username and OTP are prefilled:
  - user: Alex Tan
  - username: `alextan`
  - OTP: `123456`
- The app generates both keys and calls `POST /auth/devices` twice: the device key with `scope: "full"` and the Peek key with `scope: "peek"`.
- An install that lacks either key or binding shows "Set up this iPhone" again.
- The web demo binds silently on load with a generated key kept in `localStorage`.

## Sessions

- The access JWT lasts 5 min. The refresh token lasts 30 min and rolls on use.
- The client idle timeout is 5 min since the last touch. After it, the next action that needs data asks Face ID once more and carries on in place.
  - The form keeps its fields.
- A 401 from any service triggers the same Face ID re-check once.
- A second 401 sends the user back to the entry screen.

## Errors

Every error body is `{"code": "...", "message": "..."}`.

A token with a `scope` claim reaches only the endpoints that allow that scope. Every other endpoint answers 403 `SCOPE_NOT_ALLOWED`. Today `peek` is the only scope, and only `GET /accounts/peek` allows it.

## Auth service (8081)

- `POST /auth/devices` registers a device:
  - request: `{username, otp, deviceName, publicKey, scope?}`, where `publicKey` is a base64 X9.63 P-256 public key
  - `scope` is `full` (the default) or `peek`
  - response 201: `{deviceId, userId}`
  - errors: 400 `BAD_SCOPE`, 401 `BAD_OTP`
- `POST /auth/challenge`:
  - request: `{deviceId}`
  - response: `{nonce, expiresAt}`
  - the nonce is valid for 60 s
- `POST /auth/session`:
  - request: `{deviceId, nonce, signature, scope?}`, where `signature` is base64 DER ECDSA SHA-256 over the nonce's UTF-8 bytes
  - response: `{accessToken, refreshToken, expiresAt}`
  - errors: 400 `BAD_SCOPE`, 401 `DEVICE_UNKNOWN`, 401 `BAD_SIGNATURE`, 401 `NONCE_EXPIRED`, 403 `SCOPE_NOT_ALLOWED`
  - a device registered with `scope: "peek"` gets only Peek passes. Asking it for a full session is 403 `SCOPE_NOT_ALLOWED`.
  - on `DEVICE_UNKNOWN`, the client runs first-run setup again
  - `scope: "peek"` asks for the read-only Peek pass:
    - it uses the same challenge and signature, and the client asks no Face ID for it
    - response: `{accessToken, expiresAt}` with no refresh token
    - the token lasts 60 s (`auth.peek-ttl`) and carries `scope: "peek"`
    - the client gets a new pass when the old one is about to expire
  - any other `scope` value is 400 `BAD_SCOPE`
- `POST /auth/refresh`:
  - request: `{refreshToken}`
  - response: same shape as `/auth/session`
  - errors: 401 `REFRESH_EXPIRED`
- JWT:
  - HS256 with a shared secret from the `JWT_SECRET` environment variable, so every service can verify it
  - claims: `sub` (userId), `deviceId`, `iat`, `exp`, and `scope` on a Peek pass only
- Tables:
  - `users(id, username, display_name)`
  - `devices(id, user_id, public_key, name, scope, created_at, revoked_at)`, where `scope` is `full` or `peek`
  - `refresh_tokens(token_hash, device_id, expires_at)`
  - `nonces(nonce, device_id, expires_at)`

## Account service (8082)

- `GET /accounts/summary` takes the Bearer token and supports `ETag` and `If-None-Match` (304).
- Response:

```json
{
  "displayName": "ALEX TAN",
  "accounts": [
    {
      "id": "acc-1",
      "name": "Everyday Savings",
      "numberMasked": "•••• 1234",
      "balance": "2,345.67",
      "available": "2345.67",
      "currency": "SGD"
    }
  ],
  "paynowDailyLimit": "5000.00",
  "paynowUsedToday": "0.00",
  "updatedAt": "..."
}
```

- `balance` is display text. `available`, `paynowDailyLimit` and `paynowUsedToday` are decimal strings.
- A Peek pass on `/accounts/summary` is 403 `SCOPE_NOT_ALLOWED`.
- `GET /accounts/peek` takes the Bearer token of a Peek pass or a full session. It returns the first deposit account (lowest `id`) and its latest 3 transactions from the last 30 days, newest first:

```json
{
  "balance": "2,345.67",
  "currency": "SGD",
  "asOf": "2026-11-20T09:32:00.123Z",
  "transactions": [
    { "type": "PayNow Transfer", "date": "2026-11-20", "amount": "-12.50" },
    { "type": "FAST Payment / Receipt", "date": "2026-11-18", "amount": "500.00" },
    { "type": "NETS Purchase", "date": "2026-11-16", "amount": "-8.40" }
  ]
}
```

- `balance` is display text, the ledger balance without holds. `asOf` is the server time. `date` is the Singapore date. `amount` is a signed decimal string, negative for money out.
- The response is `Cache-Control: no-store`. Errors: 401 with no or a bad token, 404 `ACCOUNT_NOT_FOUND`.
- Internal endpoints for the payment service, which require no user token and are reachable only from localhost:
  - `POST /internal/holds` takes `{paymentId, accountId, amount}`.
    - It checks the available balance and the daily limit atomically.
    - It returns 201, 422 `INSUFFICIENT_FUNDS` or 422 `LIMIT_EXCEEDED`.
  - `POST /internal/holds/{paymentId}/capture` also writes a "PayNow Transfer" row to `transactions`.
  - `POST /internal/holds/{paymentId}/release`
- Tables:
  - `accounts(id, user_id, name, number_masked, balance, currency)`
  - `holds(payment_id, account_id, amount, status)`
  - `paynow_usage(user_id, day, used)`
  - `transactions(id, account_id, type, amount, posted_at)`, with a captured payment's row keyed by its paymentId
- Seed data for Alex Tan:
  - Everyday Savings, SGD 2,345.67
  - Bonus Savings, SGD 10,120.00
  - PayNow daily limit SGD 5,000
  - transactions on Everyday Savings, dated relative to each start: "FAST Payment / Receipt" +500.00 (2 days ago), "NETS Purchase" -8.40 (4 days ago), "PayNow Transfer" -25.00 (9 days ago), and "GIRO Payment" -60.00 (41 days ago, outside the Peek window)

## Lookup service (8083)

- `GET /paynow/lookup?type=MOBILE|UEN&value=...` takes the Bearer token of a full session. A Peek pass is 403 `SCOPE_NOT_ALLOWED`.
- Response: `{proxyType, proxyValue, maskedName, bankCode}`
- Errors:
  - 404 `PROXY_NOT_FOUND`
  - 504 `DIRECTORY_TIMEOUT` (it calls the directory with a 2 s timeout)
  - 429 `RATE_LIMITED` (30 a minute per user)
- Hits are cached in memory for 60 s.

## Mock PayNow directory (8085)

- `GET /directory/proxies/{type}/{value}` returns `{proxyType, proxyValue, maskedName, bankCode}` or 404.
- Table: `proxies(type, value, masked_name, bank_code, latency_ms)`
- Seed data:

| Type | Value | Masked name | Bank | Notes |
|---|---|---|---|---|
| MOBILE | 91234567 | TAN ** **NG | OCBC | |
| MOBILE | 98765432 | LIM ** **AH | UOB | |
| UEN | 201912345K | KOPI **** PTE LTD | DBS | |
| MOBILE | 90000001 | SLOW ** **ER | OCBC | latency_ms 3000, so the lookup times out |
| MOBILE | 90000002 | REJ ** **ED | REJECT | Mock FAST rejects it |
| MOBILE | 80000000 | | | absent, so it's not found |

Any other well-formed proxy resolves too, so real PayNow QR codes work in the demo:
- a mobile of 8 digits starting with 8 or 9, except numbers starting 8000000
- a UEN of 9 or 10 characters

It gets a stable made-up masked name, such as "KOH ** **JE" or "LUCKY **** PTE LTD", and a bank of DBS, OCBC or UOB. Numbers starting 8000000 return 404.

## Payment service (8084)

- Both payment endpoints take the Bearer token of a full session. A Peek pass is 403 `SCOPE_NOT_ALLOWED`.
- `POST /payments/paynow` takes the Bearer token and an `Idempotency-Key` header (a UUID the form creates when it opens).
  - Request: `{fromAccountId, proxyType, proxyValue, amount, currency: "SGD", reference}`
  - Response 202: `{paymentId, status: "PENDING"}`
  - A repeat with the same key returns the same payment.
  - Errors:
    - 422 `INSUFFICIENT_FUNDS` or 422 `LIMIT_EXCEEDED`, passed through from the hold
    - 422 `PROXY_NOT_FOUND`
- Flow:
  1. Resolve the proxy through the lookup service's directory client to get `bankCode`.
  2. Place a hold.
  3. Insert into `payments`.
  4. Publish `payments.requested`.
- `GET /payments/{id}?waitMs=5000` long-polls until the status leaves PENDING or the wait ends.
  - Response: `{paymentId, status: PENDING|SETTLED|REJECTED, reason?, amount, maskedName, settledAt?}`
- It consumes `payments.settled`:
  - SETTLED → capture the hold
  - REJECTED → release it
- Table: `payments(id, idempotency_key UNIQUE, user_id, from_account_id, proxy_type, proxy_value, masked_name, bank_code, amount, reference, status, reason, created_at, settled_at)`

## Mock FAST (8086)

- It consumes `payments.requested` and waits `fast.delay-ms`:
  - 200 ms by default
  - 2000 ms with the `today` profile
  - the table's `fast.settle` with the `measured` profile
- It publishes `payments.settled`.
- `bankCode` `REJECT` gives REJECTED with reason `BENEFICIARY_BANK_REJECTED`.

## Measured latency

`latency/measured.json` holds what each backend call costs in a real banking app. The timings come from screen recordings of the real app. These are likely network times. Video frames show how long each screen was up, not what the app was doing.

| Key | ms | Where it applies |
|---|---|---|
| `auth.session` | 300 | `POST /auth/session` |
| `auth.refresh` | 300 | `POST /auth/refresh` |
| `account.summary` | 600 | `GET /accounts/summary` |
| `account.peek` | 600 | `GET /accounts/peek` |
| `lookup` | 500 | `GET /paynow/lookup` |
| `payment.submit` | 300 | `POST /payments/paynow` |
| `fast.settle` | 2000 | Mock FAST's settle delay |

The redesign's speed has to come from making fewer calls and overlapping them. Each call costs what it costs in the real app.

- **The `measured` profile:**
  - `LATENCY_PROFILE=measured scripts/up.sh` starts every service with it.
  - A shared filter in `common` (`MeasuredLatency`) waits the table's time before each endpoint above runs.
  - It reads the table from `latency.table`, which defaults to `../latency/measured.json` relative to `services/`.
  - Mock FAST settles after `fast.settle`.
  - The mock directory skips its own 150 ms for made-up proxies, so the lookup's time counts once.
  - Without the profile, no endpoint waits and the e2e suite runs at full speed.
- **The public demo** reads the same file. See "Public web demo".

## Public web demo

`pnpm build:demo` builds `web/app/apps/web` as a static site with no backend. It builds to `web/app/apps/web/dist-demo/` with Vite `base: '/demos/dbs/'`.

- **In-browser backend** (`apps/web/src/demo/`):
  - It answers every `/api/<service>/...` call inside the page, with the endpoints, bodies and error codes in this file.
  - Each visitor gets their own Alex Tan, seeded as in the account service. The state lives in `localStorage` under `dbs.demo.bank`.
  - Access and refresh tokens, nonces, the lookup cache and the rate limit live in memory for the life of the page. A reload asks Face ID again, as the app does after a restart.
  - The device key, signatures, scopes, idempotency, holds, the daily limit and settlement follow the services.
  - The mock directory uses the same seeded rows and the same made-up names as `DirectoryController.java`.
  - Each call waits its time from `latency/measured.json`. A payment settles `fast.settle` after it's submitted.
- **Routing:** the app keeps its screens in memory and never changes the URL, so a refresh at the base path always lands on the entry screen.
- **Privacy:**
  - Nothing a visitor enters leaves the browser. The demo loads its own files and makes no other request. There's no analytics.
  - The entry screen and the PayNow form show "Demo. Nothing you enter leaves this device. Recent payees stay in this browser until you reset the demo in More."
  - More → About this demo shows "Network times simulated from timings measured in a real banking app." and a "Reset demo" button. Reset wipes every `dbs.*` key in `localStorage` and reloads.
- **Recent payees** (every build):
  - After a settled payment, the host keeps the proxy and masked name in `localStorage` under `dbs.recentPayees`, newest first, up to 5.
  - The PayNow menu lists them as one-tap rows above "Local transfer". A row opens the form with the proxy filled in.
  - "Clear" wipes them.
- **Verify:** `pnpm --filter web preview:demo` serves the build at `http://localhost:4173/demos/dbs/`. `pnpm e2e:demo` runs the journeys against it and blocks every request to another origin.

## Kafka events (JSON, key = paymentId)

- `payments.requested`: `{paymentId, fromAccountId, proxyType, proxyValue, bankCode, amount, currency, reference, requestedAt}`
- `payments.settled`: `{paymentId, status: "SETTLED"|"REJECTED", reason, settledAt}`

## SGQR (`packages/sgqr`, mirrored in Swift)

- An EMVCo TLV parse with a CRC16-CCITT check on tag 63.
- PayNow sits in a merchant account template (tags 26 to 51) whose sub-tag 00 is `SG.PAYNOW`. Its sub-tags:
  - 01: proxy type, `0` = MOBILE, `2` = UEN
  - 02: proxy value
  - 03: amount editable, `0` or `1`
  - 04: expiry `YYYYMMDD`
- Tag 54 is the amount. Tag 62 sub-tag 01 is the bill reference.
- Mobile values may carry `+65`, which is stripped to 8 digits.
- A non-PayNow QR gives the error "This QR isn't a PayNow code". The scanner shows it and keeps scanning.
- Sample QRs (PNG and raw string) for 91234567 at SGD 12.50, the UEN with an editable amount, and a non-PayNow code live in `web/app/packages/sgqr/samples/`.

## PayNow form ↔ host bridge

The form never holds the session token.

- **Init:**
  - The host sets `window.__PAYNOW_INIT__` before the bundle loads, or calls `window.paynowForm.open(init)`.
  - `init = {proxyType?, proxyValue?, amount?, amountEditable, reference?, source: "qr"|"menu"}`
- **Host interface:**
  - On the web, the host sets `window.paynowHost`.
  - On iOS, a native shim injected at document start implements the same interface over `window.webkit.messageHandlers.paynow` with promise ids.

```ts
interface PaynowHost {
  api(service: "account"|"lookup"|"payment", path: string, init?: {method?: string; body?: unknown; headers?: Record<string,string>}): Promise<{status: number; body: unknown}>
  // the host adds the Bearer token, refreshes it, and runs the one Face ID re-check on idle or a 401
  done(result: {paymentId: string; status: "SETTLED"|"REJECTED"; amount: string; maskedName: string}): void
  close(): void
  pickContact?(): Promise<{name: string; phone: string} | null>
  // optional: the host opens its contacts list and resolves the picked person, or null when closed
}
```

- **Contacts:**
  - The form shows a contacts button (`#pf-contacts`, "Choose from contacts") in the Mobile number field when the host defines `pickContact`. The web host leaves it out, so the web shows no button.
  - The form strips spaces, dashes, brackets and a leading +65 from the picked `phone`, or 65 when 10 digits remain. A valid SG mobile fills the field and runs the usual lookup. Anything else shows "Pick a Singapore mobile number".
  - The picked `name` shows as "From contacts: <name>" under the masked name. It stays on the device and never reaches a service.
  - iOS lists the user's contacts in its own sheet, with one row per SG mobile. Contact data stays on the phone. Only the chosen number goes to the lookup, the same as a typed one.

- **Form states:**
  - Lookup pending shows the name as a skeleton.
  - `PROXY_NOT_FOUND` shows "No PayNow account for this number".
  - `DIRECTORY_TIMEOUT` shows "Couldn't check the name" with Retry.
  - Pay is disabled until a name resolves.
  - An amount over `available` shows "Not enough in this account". An amount over the remaining limit shows "Over your PayNow daily limit". Pay is disabled for both.
  - On Pay, the button locks and shows a spinner. A retry reuses the same Idempotency-Key.
  - REJECTED shows "Payment didn't go through. No money left your account."

## Look

- A red accent (`#E1251B`) on white, system font, Liquid Glass tab bar.
  - iOS uses the native glass APIs (`.glassEffect`, `TabView`).
  - The web imitates them with backdrop-filter.
- Home has "Hi, ALEX TAN!", a balance-hide eye toggle that persists, and Scan & Pay where Insights is.
- Tabs: Home, Pay & Transfer, Wealth, Apply, More. Each tab keeps its scroll position and data.
- A failed background refresh keeps the last data and shows "Updated N min ago".
